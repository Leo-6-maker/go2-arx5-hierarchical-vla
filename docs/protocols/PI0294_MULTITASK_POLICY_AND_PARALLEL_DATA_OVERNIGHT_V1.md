# PI0294：双任务仿真 Policy 与并行数据生产夜间 Goal

## 0. 目标、范围与接手方式

### 首要目标

在固定底座 ARX5 的真实 MuJoCo 接触仿真中，得到**同一份 GR00T checkpoint**，仅根据语言和真实观测，分别完成：

| 任务                    | 指令语义             | 必须出现的物体行为               |
| --------------------- | ---------------- | ----------------------- |
| **T1：Pick-and-place** | 抓起方块，放入目标区，释放并撤离 | 持续抓握、抬升、搬运、释放、稳定保持      |
| **T2：Push-to-target** | 沿桌面把方块推入目标区，不要抓起 | 实际接触推动、桌面位移、不抓举、分离并稳定保持 |

**两种颜色、两个方向或者两个不同目标位置，不单独算两种操作技能。** 本轮必须有抓放与推送这两种不同的接触行为。

第二目标是建立可复用的：
```
CoreLab 多进程采集
        ↓
独立审计、原生数据导出、冻结数据版本
        ↓
Hopper 部分微调与闭环评估
```

本轮不训练或修改师兄的 WBC，不进行移动 Go2 或真机实验。研究主线仍是任务空间物体操作学习；WBC 是后续冻结执行器接入对象，而不是本轮重新开展的控制器训练项目。

## 1. 夜间调度：三条工作线同时推进

### 工作线分工

| 工作线           | 执行位置                        | 主要工作                             |
| ------------- | --------------------------- | -------------------------------- |
| **A：数据生产**    | CoreLab 4080S 的已验证环境、本地 SSD | 新推送任务、场景参数化、2→4 worker 真实采集      |
| **B：数据审计与制作** | CoreLab 可用 CPU；按本机路径资格执行    | 原始审计、窗口导出、统计、冻结 manifest、HF 增量交付 |
| **C：模型学习与评价** | Hopper 的合法 H200 allocation  | 模型工程测试、双任务微调、离线诊断、真实反馈闭环         |
| **协调与中继**     | 现有 local-pc owner           | 唯一任务账本、资源分配、Git 发布、双 SSH 观测／动作中继 |

**唯一协调 owner 不等于只能有一个采集进程。** 它负责分配任务，worker 负责独立执行。

### 并行关系
```
CoreLab：
推送任务资格 → 小型双任务数据 v3.0 → 继续扩采 v3.1
                         │                    │
                         │                    └→ 审计、归档，供后续训练
                         ↓
Hopper：
认证/模型检查 ─────────→ 只用冻结 v3.0 训练 → 闭环验证
```

核心原则：

**先用足量的小型双任务包启动训练；之后采集的数据进入 v3.1，不临时加入正在训练的 v3.0。**

进入闭环评估时，CoreLab 优先为评估环境保留 CPU；扩采 worker 可以在 episode 边界降到一个或暂停，不能抢占导致推理中继超时。

### 与 PI0292 的关系

先核对实际进程，而不是只看旧报告：

- PI0292 有健康运行中的作业：不终止、不热更新，按其阶段边界交接。
- PI0292 仍未启动神经模型：保留其数据、失败记录和资格结果，**不要求先跑完原单任务 S0–S6 才能开展本轮多任务学习**。
- 本轮新训练属于 PI0294；不能改称 PI0292 原先预注册的 B1。
- 已通过且代码、环境、数据语义未改变的工程验收可以复用，不重复跑整套历史检查。
- 原账本不归零。本夜总资源视图必须同时显示仍在继续的 PI0292 消耗与 PI0294 新消耗，重叠时间不重复计算。

## 3. 多任务场景必须如何构建

### 3.1 共用底座，不重建整个机器人系统

复用已验证的 ARX5 六轴运动链、夹爪、有限力矩驱动、物体动力学与双相机采集。

本轮先保持以下因素不变：
```
MuJoCo 与现有固定版本
机械臂和夹爪结构、控制器参数
物理步长 0.002 秒
观测频率 20 Hz
H40、执行 prefix8
256×256 双 RGB
EEF10 动作语义
固定桌高、物体尺寸与质量
```

**先不要同时改变物体形状、摩擦、桌高、机器人结构和控制增益。** 首夜优先解决两种任务行为及可辨识的场景变化。

### 3.2 抓放与推送必须共享相同初态

对于成对场景，T1 和 T2 的以下内容必须相同：
```
机器人初始关节和夹爪状态
物体初始位置、姿态和零初速度
目标区域
相机、灯光、背景
```

**仅任务指令不同。**

例如：
```sql
T1:
Pick up the red cube, place it inside the blue square,
release it, and move the gripper away.

T2:
Push the red cube along the table into the blue square
without lifting it, then move the gripper away.
```

不要通过“推送任务初始就闭爪、抓放任务初始就开爪”给模型提供捷径；也不要让推送任务固定出现在一种背景里。

这类配对既要出现在训练数据，也要出现在独立确认集。

### 3.3 四类场景

以下是**本轮设计范围，不是现有代码已全部实现**：

| 场景族             | 变化内容                   | 实施要求                  |
| --------------- | ---------------------- | --------------------- |
| **F0：基础同场景双任务** | 已验证桌面布局，加入同初态推送行为      | 最快获得两技能训练样本           |
| **F1：空间变化**     | 扩大起点／目标变化，平衡正向与反向搬运／推送 | 保持机器人可达、完整动作扫掠空间无非法接触 |
| **F2：视觉变化**     | 中性桌面材质、背景、灯光变化         | 红色物体和蓝色目标仍可辨识；物理参数不变  |
| **F3：组合变化**     | F1＋F2，追加小幅相机安装扰动       | 单独记录标定；主要进入扩展包与挑战集    |

F1 可从原布局附近逐步扩展，初始候选范围建议为物体与目标 X 位于约 `0.42–0.48 m`，Y 在桌面正负方向内选择，起点到目标距离约 `0.14–0.22 m`。这些是**候选范围**：必须通过现有机器人模型的几何、IK、视野和接触资格，不能直接宣称整片空间可用。

F2 灯光强度可先在基准的 `0.8–1.2` 倍范围变化，背景使用不与目标颜色混淆的中性色。

F3 相机先限制为约 `±1 cm` 平移、`±3°` 姿态扰动；不是任意随机视角。扰动后仍需保存真实外参和有效目标可见性。

### 3.4 推送 Teacher 与评分必须真正独立成立

推送 Teacher 应实现：
```
接近物体侧面
→ 到达可接触的推送位姿
→ 建立真实接触
→ 沿桌面推进
→ 脱离物体
→ 撤离并保持
```

推送接触位姿必须按**实际夹爪碰撞几何**计算，不能假定 TCP 点就是推杆尖端。

推送成功至少要求：

- 有实际机器人—物体接触和至少 `10 cm` 的水平位移。
- 没有形成持续 `0.3 s` 的双侧抓握。
- 物体没有被抬起；本轮将允许的中心高度上升限定为 `5 mm`，数值接触容差单独记录。
- 最终物体完整进入目标区，机器人已脱离。
- 沿用原最终保持区间与运动／安全检查，不因首次进入目标区就提前停止。

抓放继续沿用已经验证的完整任务谓词。

**不得通过修改物体位姿、隐藏外力、weld、任务答案控制在线策略或评分放宽来获得成功。**


## 5. CoreLab 并行采集：先真实验证，再扩大

现有准备只证明两个合成 worker 能运行，并没有证明真实 MuJoCo worker 已经接入。应复用该框架补齐，不从头再写另一套。

### 5.1 执行结构
```
Coordinator
  ├── worker-0：独立 MuJoCo、渲染上下文、episode 目录
  ├── worker-1：独立 MuJoCo、渲染上下文、episode 目录
  ├── worker-2：资格通过后启用
  └── worker-3：资格通过后启用

独立 Auditor / Exporter
  └── 只读取已完成、已封存的 episode
```

采用 `spawn` 创建进程，每个 worker 独立持有仿真状态；不同任务场景也独立构造模型。不要跨进程共享可变 `MjData` 或已经初始化的渲染上下文。MuJoCo 官方也将独立状态的采样并行与单条时间积分区分开来。[Mujoco](https://mujoco.readthedocs.io/en/3.2.7/programming/simulation.html)

### 5.2 并发与资源

默认 **2 个 worker**，每个先分配最多 3 个 CPU 核；验证后最多增加到 **4 个 worker**。

采集、审计、打包和协调的项目总并发上限为 **16 个已获准 CPU 核**，且不得超过实际空闲与允许使用的资源。不能按机器总核数直接占满。

给 Mesa、BLAS、OpenMP 显式设置线程数和互不重叠的 CPU affinity，避免四个进程都抢相同的前四个核。

### 5.3 必须完成的并行资格

用独立诊断布局比较串行和并行：

**实际物理轨迹、接触历史、提交动作、帧数、图像与状态时序、完整评分、首次尝试账本均应一致或满足预先规定的数值容差。**

采用同一渲染后端时检查像素一致性；不能把改用另一渲染器也归入“纯并行提速”。

吞吐测量使用真实 `wall_s` 和准入 episode／小时。**不能把 CPU 秒直接当作墙钟时间，也不能声称四 worker 必然四倍快。**

并行不提速或影响正确性时，自动回退到已经通过的并发级别，但保持原数据和失败记录。

### 5.4 写入与预算必须集中管理

Coordinator 在启动前原子预留 episode ID、积分、CPU、内存和空间；worker 不同时读写同一份总 JSON 账本。

每个 episode 使用独立输出目录，完成后写最终 manifest／READY，再交给审计器。超时或失联不能无条件把 ID 重新分配；先核实原 PID、启动身份和已发生的物理步数。

可异步编码 PNG、计算 hash、制作视频，但队列必须有上限，满时阻塞，**不允许丢帧**。视频制作不占用下一条采集的物理槽位。

## 6. Hopper：以第一次真实双任务学习为中心

### 6.1 不要求先完成旧单任务正式实验

若 PI0292 尚未开展神经训练，本轮不必先耗完整个晚上完成旧 4096 步与旧确认流程。

复用已经合格的数据和模型工程准备，直接为 PI0294 建立新任务清单。旧 PI0292 缺失的模型结果保持 `NOT_RUN`，不追溯改写。

如果双任务 v3.0 尚未就绪，而 Hopper 已获得合法资源，可先执行真实模型 smoke。不要让 GPU 长时间驻留空等数据；没有下一可执行工作时释放 allocation。

### 6.2 微调范围

本轮采用一份共享 GR00T：

| 项目                             | 配置                              |
| ------------------------------ | ------------------------------- |
| 初始化                            | 已核验的官方 `GR00T-N1.7-3B` 固定版本     |
| 视觉／语言骨干                        | 冻结                              |
| State/action projector 与动作 DiT | 训练，记录实际参数集合                     |
| 输入输出                           | 双 RGB＋语言＋实际 EEF10 → H40×EEF10   |
| Loss                           | 官方 masked flow-matching         |
| 有效 batch                       | 32                              |
| 学习率                            | `1e-4`                          |
| 优化器／精度                         | AdamW、BF16                      |
| 学习率计划                          | cosine，warmup 5%                |
| 常规目标                           | 4096 optimizer steps            |
| 绝对上限                           | 6144 optimizer steps            |
| 多任务方式                          | 同一权重、同一 processor、同一统计，不按任务切换模型 |

不同时加入 LoRA、全模型解冻、新辅助 loss、世界模型或 WBC 补偿。

### 6.3 采样不能被旧抓放与保持帧主导

任务采样概率固定为：
```ini
T1 = 50%
T2 = 50%
```

T1 内部来自旧 64 条数据的曝光占比不超过三分之一，保证新成对场景充分参与。

每个任务内部先均衡抽取场景族和 episode，再按以下锚点阶段权重采样：

| 阶段       | 权重  |
| -------- | --- |
| 接近       | 20% |
| 建立接触／抓握  | 25% |
| 搬运／推送    | 25% |
| 释放／脱离与撤离 | 20% |
| 保持       | 10% |

这是**本轮明确声明的新训练配方**，不是声称原 PI0292 已采用这种采样。

阶段信息仅用于离线选样，不输入模型。空 bucket 必须显式处理和记录，不为满足精确全局配额重新制造不可行采样约束。记录实际样本曝光，而不只记录期望比例。

### 6.4 快速观察策略，但不污染最终确认

训练后保存：
```
M512
M2048
M4096
必要时 M6144
```

M512 先在少量 TRAIN 布局做闭环开发检查，目的在于尽早发现“始终保持”“不开爪”“动作全被拒绝”等灾难性问题，不叫泛化评估。

M2048 和 M4096 在固定 DEV 子集上各评价每任务 4 条。只有当 M4096 相比 M2048 的总成功数增加至少 2，且每任务至少有 1 条成功、没有真实安全违规，并且时间与资源允许时，才执行预先允许的额外 2048 步。否则不自动续训。

候选选择规则在训练前固定：

**优先最大化两个任务中较低的 DEV 成功率，其次看宏平均，再看拒绝率；完全相同时选较早 checkpoint。**

选定后冻结唯一候选，再打开确认集。不得按最终确认结果重新挑模型。

## 7. 模型和数据提速：只做收益清楚的优化

本夜优先处理已经准备过、风险较低的热点：

**第一，Hopper 本地不可变数据缓存。** 完整校验固定数据版本后，避免每次随机采样都从远端拉文件。接入有界的 decoded-RGB LRU 和数值 episode 缓存；缓存键包含数据、图像和处理配置的身份。

**第二，测试 DataLoader 的 0／2／4 worker。** 保持实际样本顺序与消费 cursor 一致，预取不能当成优化器已经消费。使用测得更快且通过一致性检查的配置。

**第三，在主训练前测 microbatch。** 可比较 `2×16`、`4×8`、`8×4`，始终保持有效 batch 为 32。选择在显存内稳定、吞吐最高的一档，再封存，不能训练中按成绩随意改变。

本夜不切换仿真引擎，不移植 Isaac Lab，不做大规模 `torch.compile`／量化／冻结 VLM 特征缓存改造。后者可以有价值，但不应再次成为第一版 Policy 的前置工程项目。

模型工程 smoke 最多 16 个真实更新；连续与恢复路径使用相同样本和随机性，验证真实梯度、冻结模块和完整恢复状态。测试权重不冒充正式候选。

## 8. “多任务可行”必须怎样验收

### 8.1 使用真实新观测闭环

复用已经准备的 ACK 中继组件，补齐实际部署与端点验证。当前记录中的 CPU 协议通过，不等于真实双 SSH／物理闭环已经通过。

循环必须是：
```
CoreLab 保存当前真实 RGB＋实际 EEF/夹爪
        ↓
Hopper 同一共享模型生成 H40
        ↓
按该观测的 TCP 和时间解码，检查安全
        ↓
只提交前 8 点
        ↓
CoreLab 推进 0.4 秒仿真
        ↓
重新观测、重新查询
```

先通过 Teacher 经相同消息和安装链的真实测试，再运行模型。

超时、旧包、重复 ACK 或未知物理进度不得导致重复执行。不得用预录轨迹回放、Teacher 接管或重复采噪声直到输出被接受，冒充模型闭环。

### 8.2 独立确认集

预先封存 16 个新场景组，每组分别执行两个任务。

其中：

- **核心集 8 组**：F0/F1/F2，验证当前训练分布附近的新场景。
- **挑战集 8 组**：包括 F3 组合变化，单独报告，不与核心集混成一个平均分。

先由 Teacher 完成相同确认条件。Teacher 失败的条件不从分母中删除；出现真实安全问题，停止该场景族继续执行。

### 8.3 第一版工作策略标准

同一份候选在核心集上：

| 项目            | 最低要求      |
| ------------- | --------- |
| 抓放            | ≥6/8 完整成功 |
| 推送            | ≥6/8 完整成功 |
| 同一场景组，两种指令都成功 | ≥5/8 组    |
| 真实安全违规        | 0         |
| Teacher 核心集资格 | 每任务 ≥7/8  |
| 旧抓放回归面板       | ≥6/8      |

这里的 8 条旧抓放回归来自单独登记的原数据验证布局，用于能力保留检查，不冒称全新盲测。

此外，推送时不能用抓起再放下的行为“完成位置目标”；抓放时也不能只推过去。

**若达到这些条件，可以报告 `MULTITASK_SIM_WORKING_V1`，但必须注明它是小规模、固定底座、两技能仿真结果，不是部署、真机或广泛泛化资格。**

未达门槛也必须交付实际模型、视频与分任务失败归因；不能只返回一份数据准备报告。
